# 1주차 — 해시와 블록 연결

해시 실습 코드 + 중앙DB/분산DB/블록체인 비교표 + 토론 답변.

---

## 1. 코드 구성

| 파일 | 역할 |
| --- | --- |
| `src/Hashes.java` | SHA-256 계산, 16진수 변환, **비트 차이 세기**(눈사태 효과 측정) |
| `src/Block.java` | 블록 객체. `previousHash` 포함, 해시는 **저장 않고 계산** |
| `src/Blockchain.java` | 체인 + 검증. 어디가 왜 깨졌는지까지 반환 |
| `src/Main.java` | 과제 1~5번 + 보너스(작업증명) 실행 |

### 설계에서 중요한 한 가지

```java
// Block.java — 해시를 필드로 저장하지 않는다
public String hash() {
    String payload = index + "|" + timestamp + "|" + previousHash
                   + "|" + String.join(",", transactions) + "|" + nonce;
    return Hashes.sha256(payload);
}
```

저장해 두면 **데이터를 고친 뒤 해시도 같이 고칠 수 있다.** 매번 계산하면 데이터가 바뀌는 순간 해시가 저절로 달라진다. 실제 블록체인도 해시를 블록 안에 담지 않고 **받는 쪽이 직접 계산해서 확인**한다.

## 2. 실습 결과

### 실습 3 — 눈사태 효과 (핵심)

```
원본  : 보험금 1,000,000원
해시  : 8d0480fc7fb9d3373d20baa9a568cc63f1ed6db8297554cef3af9954a34e4105

변경  : 보험금 1,000,001원     ← 마지막 한 글자만
해시  : c57b5db8acdefe307665dcac4d9c4605a9e0f5c9e3fe7fc499efeb1c4795565d

다른 비트 수 : 118 / 256  (46.1%)
```

> **한 글자 바꿨는데 비트의 약 절반이 뒤집혔다.** 이게 눈사태 효과다.
> "비슷한 입력 → 비슷한 출력"이면 원문을 역추적당하므로, 조금만 바꿔도 완전히 달라져야 안전하다.

같은 입력은 몇 번을 해도 같은 출력이 나온다(**결정성**). 그래서 누가 어디서 계산하든 검증이 가능하다.

### 실습 5 — 변조 탐지

블록 1의 거래를 `100만원 → 9999만원`으로 고쳤을 때:

```
블록    변조 전                변조 후
0     13b1ee8e7560...e714    13b1ee8e7560...e714
1     23f382bd4ccf...fac5    c7a2391e12f1...f58e   ← 바뀜
2     75d0201e76c8...6f8f    75d0201e76c8...6f8f
3     88b5c8b88477...c3c8    88b5c8b88477...c3c8

검증 : 실패 ✗ (블록 2)
   블록 2 의 previousHash 가 블록 1 의 실제 해시와 다릅니다
   기대: 23f382bd4ccf...fac5
   실제: c7a2391e12f1...f58e
```

고친 건 블록 1 하나인데, 블록 2가 **이미 저장된 옛 해시**를 들고 있어서 어긋난다. 데이터 무결성의 실체가 이 한 줄 비교다.

### 보너스 — 작업증명 비용

```
난이도   시도 횟수      걸린 시간
0 1          14           0 ms
0 2         113           2 ms
0 3       4,619          20 ms
0 4      26,896          30 ms
0 5   3,697,426       1,334 ms
```

난이도가 1 오를 때마다 **약 16배**로 뛴다(16진수 한 자리가 0일 확률 1/16). 비트코인 실제 난이도는 0이 19개쯤이다.

> 변조를 막는 방식이 **"불가능"이 아니라 "수지가 안 맞음"** 이라는 게 핵심이다.

## 3. 산출물 — 중앙 DB / 분산 DB / 블록체인 비교표

### 한눈에

| | 중앙 DB | 분산 DB | 블록체인 |
| --- | --- | --- | --- |
| **예시** | Oracle, MySQL 단일 | MySQL 클러스터, Cassandra, MongoDB | 이더리움, 비트코인, Hyperledger |
| **서버 대수** | 1대(+백업) | 여러 대 | 여러 대 |
| **결정권자** | **1곳** | **1곳** (같은 조직) | **여러 곳** |
| **신뢰 모델** | 운영자를 신뢰 | 운영자를 신뢰 | **아무도 신뢰 안 함** |
| **장애 가정** | — | 크래시 장애 | **비잔틴 장애(거짓말)** |
| **쓰기 권한** | 운영자 | 운영자 | 키를 가진 누구나 |
| **데이터 수정** | `UPDATE` 로 즉시 | `UPDATE` 로 즉시 | **불가** (추가만 가능) |
| **삭제** | 가능 | 가능 | **불가** |
| **이력 추적** | 별도 설계 필요 | 별도 설계 필요 | **구조 자체가 이력** |
| **성능** | 초당 수만~수십만 | 초당 수만~수백만 | **초당 15~수천** |
| **저장 비용** | 낮음 | 낮음 | **매우 높음** |
| **합의 비용** | 없음 | 낮음 (Raft/Paxos) | **높음 (PoW/PoS)** |
| **검열 저항** | 없음 | 없음 | **있음** |
| **단일 장애점** | 있음 | 부분적 해소 | **없음** |

### 핵심 축은 두 개다

```
         분산(Distributed)         ≠         탈중앙(Decentralized)
         "컴퓨터가 여러 대인가"                "결정권자가 여러 명인가"
              물리적 배치                          권한 구조
```

|  | 중앙집중 권한 | 탈중앙 권한 |
| --- | --- | --- |
| **단일 서버** | 옛날 메인프레임 | (거의 없음) |
| **분산 서버** | **은행 시스템 · AWS** | 이더리움 · 비트코인 |

> ⚠️ **은행은 서버가 수백 대로 "분산"돼 있지만 완전한 "중앙집중"이다.** AWS도 전 세계에 분산돼 있지만 Amazon이 끄면 끝난다.
> **분산 = 성능·가용성**을 위한 것, **탈중앙 = 권력 분산**을 위한 것. 목적이 다르다.

### 선택 기준

```
중앙 DB    참가자가 한 조직. 빠르고 싸야 함          → 대부분의 업무
분산 DB    한 조직인데 규모·가용성이 필요            → 대규모 서비스
블록체인   참가자들이 서로 못 믿음. 중재자가 없어야 함  → 극소수
```

**블록체인은 성능을 버리고 "못 끄고 못 고침"을 산 것**이다. 그 교환이 가치 있는 상황에서만 쓴다.

## 4. 토론 질문

> **여러 금융기관이 데이터를 공동 검증해야 할 때 기존 DB로는 어떤 한계가 있을까?**

### 결론 먼저

**한계는 성능이 아니라 신뢰 모델이다.** 기존 분산 DB는 "참가자가 정직하다"를 **전제**하는데, 경쟁 관계인 기관들 사이에선 그 전제가 성립하지 않는다.

### ① 누구 서버에 둘 것인가 — 답이 없다

```
A은행 서버에 두면  → B, C가 "A가 몰래 고치면?" 이라고 의심
제3기관에 두면     → 그 기관을 또 믿어야 함 + 비용 + 단일 장애점
각자 따로 두면     → 데이터가 갈라짐 (현재 상황)
```

중앙 DB는 **반드시 운영 주체가 필요한데**, 경쟁사끼리는 그 주체를 정할 수 없다.

### ② 비잔틴 장애를 가정하지 않는다 ★ 핵심

| | 크래시 장애 | 비잔틴 장애 |
| --- | --- | --- |
| 증상 | 노드가 죽음. 응답 없음 | 노드가 **살아서 거짓말함** |
| 난이도 | 쉬움 (없는 셈 치면 됨) | 어려움 (누가 거짓말인지 모름) |
| 대응 | Raft, Paxos | PBFT, PoW, PoS |

**MySQL 클러스터·Raft는 크래시 장애만 가정**한다. 같은 회사 서버라 "죽을 수는 있어도 거짓말은 안 한다"가 당연한 전제다.

경쟁 기관끼리는 **이 전제가 깨진다.** A가 자기에게 유리하게 기록을 조작할 유인이 실제로 존재한다. 이 상황을 다루려면 비잔틴 장애 모델이 필요하고, 거기서 블록체인이 의미를 갖는다.

### ③ 변조를 "막는" 게 아니라 "탐지"해야 한다

중앙 DB에서 DBA가 `UPDATE` 하면 **흔적 없이 바뀐다.** 감사 로그를 둬도 그 로그 역시 같은 DBA가 지울 수 있다.

```
기존 DB   : 권한으로 막는다 → 권한 가진 사람은 통과
블록체인  : 수학으로 탐지한다 → 권한과 무관하게 걸린다
```

실습 5에서 본 그대로다. 거래 하나를 고치면 뒤 블록 전부가 어긋나 **누구나 즉시 알아챈다.**

### ④ 대사(reconciliation) 비용

현재 금융권의 실제 작업 방식이다.

```
A은행 장부 ──┐
B은행 장부 ──┼─▶ 매일 대조 → 불일치 발견 → 수작업 조사 → 정정
C은행 장부 ──┘
```

**각자 자기 장부를 들고 있어서 맞춰보는 일**이 끝없이 생긴다. 사람·시간·분쟁 비용이 실제로 크다.

공유 원장을 쓰면 **애초에 하나의 장부**라 대사할 대상이 없어진다. 이게 금융권이 블록체인에 관심을 갖는 가장 현실적인 이유다.

### ⑤ 부인 방지(non-repudiation)

```
기존 DB   : "우리 시스템 기록엔 이렇게 돼 있다"  → 상대가 부인 가능
블록체인  : 개인키 서명이 붙어 있다              → 부인 불가
```

서명은 본인만 만들 수 있으므로 "나는 그런 지시를 한 적 없다"가 통하지 않는다. 분쟁 해결 비용이 크게 줄어든다.

### 균형 잡기 — 블록체인이 만능은 아니다

토론에서 이 부분까지 말하면 좋다.

```
해결하는 것:  신뢰 문제, 대사 비용, 부인 방지, 검열 저항
해결 못 하는 것:
  · 성능 (여전히 느리다)
  · 입력 데이터의 진실성 — 쓰레기를 넣으면 '변조 불가능한 쓰레기'가 됨
  · 오프체인 세계와의 연결 (오라클 문제)
  · 개인정보 (지울 수 없으니 GDPR·개인정보보호법과 충돌)
```

> 🔴 **마지막 항목이 금융권에서 특히 중요하다.** 삭제가 불가능하다는 성질이 **개인정보 파기 의무와 정면으로 부딪힌다.** 그래서 실무에서는 개인정보를 온체인에 두지 않고, **해시값만 올리고 원본은 오프체인**에 두는 설계를 쓴다.

### 그래서 실무 답은 보통 "프라이빗 블록체인"

```
퍼블릭 (이더리움)      누구나 참여. 완전 탈중앙. 느리고 비쌈
프라이빗/컨소시엄      허가받은 기관만 참여 (Hyperledger Fabric 등)
  → 참가자를 알고 있으니 PoW 불필요 → 훨씬 빠름
  → 하지만 "서로 못 믿는다"는 전제는 유지 → BFT 합의 사용
```

금융 컨소시엄에는 **퍼블릭보다 컨소시엄 체인이 현실적**이다. 속도를 얻으면서 비잔틴 장애 대응은 유지할 수 있다.

## 5. 교재 개념 정리

### 노드 vs 피어

**같은 컴퓨터를 보는 두 관점**이다.

```
노드(Node)   네트워크에 참여한 컴퓨터 한 대   → 혼자 봤을 때
피어(Peer)   나와 직접 연결된 다른 노드       → 관계에서 봤을 때
```

P2P에 서버/클라이언트 구분이 없는 이유 — **모두가 요청도 하고 응답도 한다.**

| 노드 종류 | 보관 | 역할 |
| --- | --- | --- |
| 풀 노드 | 전체 블록 + 상태 | 모든 걸 직접 검증 |
| 라이트 노드 | 블록 헤더만 | 필요할 때 풀 노드에 질의 |
| 아카이브 노드 | 전체 + 모든 과거 상태 | 과거 시점 조회 (수 TB) |

### 브로드캐스팅 — 가십 프로토콜

전체에 한 번에 뿌리는 게 아니라 **소문 퍼지듯** 번진다.

```
1단계: 연결된 피어 8~13명에게만
2단계: 받은 피어가 또 자기 피어들에게
3단계: ... 몇 초 안에 전 세계
```

중복이 많이 생기지만 **그게 설계다** — 일부 노드가 죽거나 거짓말해도 전파가 안 끊긴다.

### 검증은 전파보다 먼저 일어난다

```
트랜잭션 수신
  ↓
① 서명이 올바른가?   ← 아니면 버림. 전파 안 함
② nonce 가 맞나?
③ 잔액이 충분한가?
④ 가스가 충분한가?
  ↓
통과한 것만 mempool 에 넣고 피어에게 전파
```

> **쓰레기는 한 홉도 못 간다.** 첫 번째 피어가 걸러낸다.

### 합의(Consensus) — 왜 필요한가

```
노드 A가 받은 순서:  tx1 → tx2
노드 B가 받은 순서:  tx2 → tx1     ← 네트워크 지연으로 흔한 일

잔액 10, tx1=송금 8, tx2=송금 5 라면
  A: tx1 먼저 → 잔액 2 → tx2 실패
  B: tx2 먼저 → 잔액 5 → tx1 실패
  → 두 노드의 DB가 영구히 갈라짐
```

**이중지불의 본질은 돈 복사가 아니라 순서 불일치**다. 해결책은 **한 번에 한 명만 순서를 정하게** 하는 것(PoW 당첨자 / PoS 제비뽑기). 나머지는 그 순서를 받아 검증만 한다.

## 1. 코드 구성

| 파일 | 역할 |
| --- | --- |
| `src/Wallet.java` | 키 쌍 생성(EC·RSA), 주소 유도, 서명·검증 |
| `src/Transaction.java` | 거래 데이터. **서명 대상 직렬화**와 변조용 메서드 |
| `src/EthTxSpec.java` | 이더리움 트랜잭션 필드 명세 + 가스비 계산 |
| `src/SignatureMain.java` | 실습 1~6 + 보너스(은행 vs 블록체인) 실행 |

### ⚠️ 곡선 선택 — JDK에는 secp256k1이 없다

이더리움·비트코인은 **secp256k1**을 쓰는데, **JDK 16에서 SunEC가 이 곡선을 제거**했다. JDK 21에서도 실패한다.

```
InvalidAlgorithmParameterException: Curve not supported: secp256k1 (1.3.132.0.10)
```

그래서 JDK 표준인 **secp256r1 (NIST P-256)** 로 실습한다. 둘 다 256비트 타원곡선 ECDSA이고 **곡선 상수만 다르다.** 실제 이더리움 키를 다뤄야 하면 BouncyCastle이나 web3j가 필요하다.

> 주소 유도도 같은 이유로 대체했다. 이더리움은 **keccak256**을 쓰는데 JDK 표준에 없다 — JDK의 `SHA3-256`은 keccak256과 **패딩이 달라서 값이 다르게 나온다.** 여기서는 SHA-256으로 대체했다.

### 설계에서 중요한 한 가지 — 서명 대상 직렬화

```java
// Transaction.java — 구분자 없이 이어 붙이면 안 된다
private static final char SEP = '\u001F';  // ASCII Unit Separator
```

구분자 없이 붙이면 **서로 다른 거래가 같은 바이트열**이 된다.

```
from="0xAB", to="0xCD",  amount=12   →  "0xAB0xCD12"
from="0xAB", to="0xCD1", amount=2    →  "0xAB0xCD12"   ← 같다!
```

한쪽 서명이 다른 쪽에도 통한다. 그래서 값에 등장할 수 없는 구분자를 넣고 필드 이름까지 적는다. 이더리움은 **RLP 인코딩**으로 같은 문제를 해결한다.

## 2. 실습 결과

### 실습 1 — 키 쌍 생성

```
알고리즘 : EC/secp256r1
개인키   : 3041020100301306...575ea551  (67바이트)
공개키   : 3059301306072a86...54441249  (91바이트)
주소     : 0x5380971d01ba07e7262afcb55045ff044e60743f
```

> **개인키 → 공개키 → 주소는 한 방향으로만 간다.** 주소를 봐도 공개키를 모르고, 공개키를 봐도 개인키를 모른다.
>
> 그리고 **개인키는 사실상 그냥 256비트 난수다.** 만드는 데 계산이 필요 없다. 비밀이 지켜지는 건 어려워서가 아니라 **경우의 수가 커서**다.

### 실습 3 — 같은 데이터를 두 번 서명하면 다른 서명이 나온다

```
1회차 : 3044022078d3...3929
2회차 : 3044022053fa...c723
같은가 : false

1회차 검증 : true
2회차 검증 : true     ← 둘 다 유효하다
```

ECDSA는 서명할 때마다 **난수 k**를 새로 뽑기 때문이다.

> 🔴 **이 난수가 약하면 개인키가 통째로 샌다.** 2010년 PS3가 k를 고정값으로 써서 서명키가 털린 사건이 있다.
> 그래서 이더리움 지갑은 **RFC 6979**로 k를 데이터에서 결정론적으로 뽑는다 — 난수 생성기를 아예 신뢰하지 않는 방식이다.

### 실습 4 — 개인키 없이 검증된다

```
검증에 쓴 것 : 공개키 + 거래 데이터 + 서명
쓰지 않은 것 : 개인키

결과 : 유효 O
말로리 공개키로 검증 : 무효 X
```

> **이게 공개키 암호의 핵심이다.** 검증자에게 비밀을 나눠 줄 필요가 없으므로 전 세계 노드가 각자 알아서 검증할 수 있다.

### 실습 5 — 변조 탐지

```
[변조 전]  1,000,000원       검증 : 유효 O
   ↓ 서명은 그대로 둔 채 금액만 고침
[변조 후]  999,000,000원     검증 : 무효 X  ← 변조 탐지

받는 주소 변조 후              검증 : 무효 X  ← 변조 탐지
```

> `payload()`에 들어간 필드는 전부 서명으로 보호된다. **거꾸로 말하면 payload()에 빠진 필드는 보호되지 않는다.**
> **"무엇을 서명 대상에 넣을 것인가"가 곧 "무엇을 지킬 것인가"다.**

### 실습 6 — 이더리움 트랜잭션 필드 (Type 2 / EIP-1559)

| 필드 | 단위 | 전송됨 | 역할 |
| --- | --- | --- | --- |
| `from` | 주소 | **✗** | 보내는 사람. 적어 넣는 게 아니라 **서명에서 역산**된다 |
| `to` | 주소 | ✓ | 받는 주소. 비우면 '새 컨트랙트 배포' |
| `value` | wei | ✓ | 보낼 ETH. 1 ETH = 10¹⁸ wei. 정수만 |
| `nonce` | 정수 | ✓ | 이 계정이 보낸 트랜잭션 일련번호 |
| `data` | 바이트 | ✓ | 컨트랙트 입력. 앞 4바이트가 함수 선택자 |
| `gasLimit` | **gas** | ✓ | 수량 한도. 무한루프 방어선 |
| `maxFeePerGas` | **gwei/gas** | ✓ | 단가 상한. 지불 한도지 지불액이 아님 |
| `maxPriorityFeePerGas` | **gwei/gas** | ✓ | 검증자에게 주는 팁. 사실상 입찰가 |
| `signature` | (r,s,v) | ✓ | ECDSA 서명. 신원 증명이자 위변조 방지 |

> 🔴 **`from`만 전송되지 않는다.** 노드가 서명에서 공개키를 역산(`ecrecover`)하고 해시해서 주소를 얻는다.
> **그래서 남의 주소를 `from`으로 "주장"하는 사기가 원천 불가능하다.** 실습 1의 `개인키 → 공개키 → 주소` 사슬이 이걸 가능하게 한다.

#### 가스 숫자 세 개 — 단위를 보면 구분된다

`gasLimit`만 **gas** 단위고 나머지 둘은 **gwei/gas** 단위다. 즉 가스비는 하나의 금액이 아니라 **[수량 × 단가]** 다.

```
baseFee 190 + 팁 10 = 단가 200 gwei
단가 200 × 가스 21,000 = 4,200,000 gwei

  소각 (아무도 못 가져감) :  3,990,000 gwei  = 0.003990 ETH
  검증자 팁               :    210,000 gwei  = 0.000210 ETH
  총 가스비               :  4,200,000 gwei  = 0.004200 ETH
```

> **`baseFee`를 소각하는 이유는 ETH 가격이 아니라 수수료 조작 방지다.**
> baseFee가 검증자 수입이면, 검증자가 **가짜 트랜잭션으로 블록을 일부러 채워** baseFee를 계속 올릴 유인이 생긴다. 자기 수입을 자기가 조작하게 되는 것이다. 태워 버리면 그 유인이 사라진다.

#### nonce가 하는 일

서명된 트랜잭션은 공개 네트워크에 떠다니므로 **복사가 가능하다.** nonce가 없으면 그 바이트열을 주워서 100번 다시 뿌리면 100번 집행된다.

```
nonce   0       1       2         3        4
       [완료]  [완료]  [가스부족]  [대기]   [대기]
                        ↑ 막힘     └──── 실행 불가 ────┘
```

동시에 **순서**도 강제한다. 2번이 묶여 있으면 3·4번은 가스를 아무리 높게 불러도 못 들어간다.

> 백엔드로 치면 **멱등키 + 시퀀스 번호**를 정수 하나로 합친 것이다.
> 푸는 법은 **같은 nonce로 다시 서명해 덮어쓰기** — 가스를 올리면 "속도 올리기", `value=0`으로 자기 자신에게 보내면 "취소"다.

## 3. 토론 질문

> **은행 시스템에서 사용하는 전자서명과 블록체인 트랜잭션 서명은 무엇이 다를까?**

### 결론 먼저

**수학은 거의 같다. 다른 것은 "누가 보증하는가"다.**

실습 코드의 `Wallet.createRsa()`로 바꾸면 **은행 쪽 알고리즘으로도 그대로 동작한다.** 그만큼 기반은 같다.

### ① 알고리즘 — 크기가 다르다

실습 코드가 실제로 측정한 값이다.

| | 알고리즘 | 공개키 | 서명 |
| --- | --- | --- | --- |
| 은행 (공인·금융인증서) | RSA 2048 | 294 B | **256 B** |
| 블록체인 | EC 256bit | 91 B | **71 B** |

보안 강도는 비슷한데 크기가 3~4배 차이다. **블록 공간이 곧 돈**이라 이 차이가 그대로 수수료가 된다. 은행은 서버에 저장하면 그만이라 이 압박이 없다.

### ② 신뢰의 뿌리 — 여기가 진짜 차이다

```
은행      CA ──보증──▶ 공개키 ──▶ 서명 검증
          "이 공개키는 김민지의 것이 맞습니다"

블록체인  공개키 ──해시──▶ 주소
          ▲ 이것이 신원 그 자체. 보증하는 기관이 없다
```

은행이 믿는 것은 **서명 자체가 아니라 CA의 보증**이다. "이 서명이 유효하다"와 "이 서명을 김민지가 했다"는 다른 문장이고, 그 사이를 CA가 메운다.

블록체인은 그 연결이 없다. 증명되는 것은 딱 하나 — **"이 거래를 승인한 자가 그 주소의 개인키를 갖고 있다."** 그 사람이 누구인지는 프로토콜이 묻지 않는다.

### ③ 그래서 갈라지는 다섯 가지

| | 은행 | 블록체인 |
| --- | --- | --- |
| **신원 확인** | 실명 — 인증서에 이름이 박힘 | 가명 — 주소만 |
| **키 분실** | 재발급 가능. 자산은 그대로 | **재발급 없음. 자산도 소멸** |
| **키 탈취** | 즉시 폐기(CRL) | **폐기 수단 없음** |
| **거래 취소** | 착오송금 반환, 지급정지 | **없음** |
| **검증 주체** | 은행 서버 (폐쇄) | 전 세계 노드 (공개) |

**키 분실이 왜 이렇게 다른가** — 은행에서는 **자산이 은행 DB에 있고 인증서는 "나임을 증명하는 수단"일 뿐**이다. 신분증을 잃어도 통장 잔고는 그대로다. 블록체인은 그 분리가 없다. **개인키가 자산에 접근하는 유일한 경로**다.

### ④ 트레이드오프

| 없앤 것 | 대가로 얻은 것 |
| --- | --- |
| CA | 누구의 허가도 없이 계정 생성 |
| 은행 서버 | 특정 기관이 검열·동결할 수 없음 |
| 거래 취소 | 제3자 중재가 불필요 |
| 계정 복구 | 보관 기관에 대한 신뢰 불필요 |

> **좋고 나쁨의 문제가 아니라 전제의 문제다.** 믿을 기관이 있는 환경이라면 은행 방식이 모든 면에서 낫다 — 더 싸고, 빠르고, 실수를 복구할 수 있다.

### 한 줄 요약

> **은행 서명은 "CA가 보증한 당신"을 증명하고, 블록체인 서명은 "이 키의 주인"을 증명한다.**
> 전자는 **신원**을 증명하고, 후자는 **권한**만 증명한다.

더 자세한 논의(계정 추상화로 키 분실을 풀 수 있는가, 금융권에서 언제 쓸 만한가)는 [docs/discussion.md](docs/discussion.md)에 있다.
