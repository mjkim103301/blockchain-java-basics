# 블록체인 기초 — Java SHA-256 실습

스터디 1주차 산출물. **해시 실습 코드 + 중앙DB/분산DB/블록체인 비교표 + 토론 답변**.

```bash
bash run.sh
```

JDK 21만 있으면 된다. 외부 라이브러리 없음 — `java.security.MessageDigest` 표준 API만 쓴다.

---

## 1. 코드 구성

| 파일 | 역할 |
| --- | --- |
| `src/Hashes.java` | SHA-256 계산, 16진수 변환, **비트 차이 세기**(눈사태 효과 측정) |
| `src/Block.java` | 블록 객체. `previousHash` 포함, 해시는 **저장 않고 계산** |
| `src/Blockchain.java` | 체인 + 검증. 어디가 왜 깨졌는지까지 반환 |
| `src/Main.java` | 과제 1~5번 + 보너스(작업증명) 실행 |

### 설계에서 중요한 한 가지

```java
// Block.java — 해시를 필드로 저장하지 않는다
public String hash() {
    String payload = index + "|" + timestamp + "|" + previousHash
                   + "|" + String.join(",", transactions) + "|" + nonce;
    return Hashes.sha256(payload);
}
```

저장해 두면 **데이터를 고친 뒤 해시도 같이 고칠 수 있다.** 매번 계산하면 데이터가 바뀌는 순간 해시가 저절로 달라진다. 실제 블록체인도 해시를 블록 안에 담지 않고 **받는 쪽이 직접 계산해서 확인**한다.

## 2. 실습 결과

### 실습 3 — 눈사태 효과 (핵심)

```
원본  : 보험금 1,000,000원
해시  : 8d0480fc7fb9d3373d20baa9a568cc63f1ed6db8297554cef3af9954a34e4105

변경  : 보험금 1,000,001원     ← 마지막 한 글자만
해시  : c57b5db8acdefe307665dcac4d9c4605a9e0f5c9e3fe7fc499efeb1c4795565d

다른 비트 수 : 118 / 256  (46.1%)
```

> **한 글자 바꿨는데 비트의 약 절반이 뒤집혔다.** 이게 눈사태 효과다.
> "비슷한 입력 → 비슷한 출력"이면 원문을 역추적당하므로, 조금만 바꿔도 완전히 달라져야 안전하다.

같은 입력은 몇 번을 해도 같은 출력이 나온다(**결정성**). 그래서 누가 어디서 계산하든 검증이 가능하다.

### 실습 5 — 변조 탐지

블록 1의 거래를 `100만원 → 9999만원`으로 고쳤을 때:

```
블록    변조 전                변조 후
0     13b1ee8e7560...e714    13b1ee8e7560...e714
1     23f382bd4ccf...fac5    c7a2391e12f1...f58e   ← 바뀜
2     75d0201e76c8...6f8f    75d0201e76c8...6f8f
3     88b5c8b88477...c3c8    88b5c8b88477...c3c8

검증 : 실패 ✗ (블록 2)
   블록 2 의 previousHash 가 블록 1 의 실제 해시와 다릅니다
   기대: 23f382bd4ccf...fac5
   실제: c7a2391e12f1...f58e
```

고친 건 블록 1 하나인데, 블록 2가 **이미 저장된 옛 해시**를 들고 있어서 어긋난다. 데이터 무결성의 실체가 이 한 줄 비교다.

### 보너스 — 작업증명 비용

```
난이도   시도 횟수      걸린 시간
0 1          14           0 ms
0 2         113           2 ms
0 3       4,619          20 ms
0 4      26,896          30 ms
0 5   3,697,426       1,334 ms
```

난이도가 1 오를 때마다 **약 16배**로 뛴다(16진수 한 자리가 0일 확률 1/16). 비트코인 실제 난이도는 0이 19개쯤이다.

> 변조를 막는 방식이 **"불가능"이 아니라 "수지가 안 맞음"** 이라는 게 핵심이다.

## 3. 산출물 — 중앙 DB / 분산 DB / 블록체인 비교표

### 한눈에

| | 중앙 DB | 분산 DB | 블록체인 |
| --- | --- | --- | --- |
| **예시** | Oracle, MySQL 단일 | MySQL 클러스터, Cassandra, MongoDB | 이더리움, 비트코인, Hyperledger |
| **서버 대수** | 1대(+백업) | 여러 대 | 여러 대 |
| **결정권자** | **1곳** | **1곳** (같은 조직) | **여러 곳** |
| **신뢰 모델** | 운영자를 신뢰 | 운영자를 신뢰 | **아무도 신뢰 안 함** |
| **장애 가정** | — | 크래시 장애 | **비잔틴 장애(거짓말)** |
| **쓰기 권한** | 운영자 | 운영자 | 키를 가진 누구나 |
| **데이터 수정** | `UPDATE` 로 즉시 | `UPDATE` 로 즉시 | **불가** (추가만 가능) |
| **삭제** | 가능 | 가능 | **불가** |
| **이력 추적** | 별도 설계 필요 | 별도 설계 필요 | **구조 자체가 이력** |
| **성능** | 초당 수만~수십만 | 초당 수만~수백만 | **초당 15~수천** |
| **저장 비용** | 낮음 | 낮음 | **매우 높음** |
| **합의 비용** | 없음 | 낮음 (Raft/Paxos) | **높음 (PoW/PoS)** |
| **검열 저항** | 없음 | 없음 | **있음** |
| **단일 장애점** | 있음 | 부분적 해소 | **없음** |

### 핵심 축은 두 개다

```
         분산(Distributed)         ≠         탈중앙(Decentralized)
         "컴퓨터가 여러 대인가"                "결정권자가 여러 명인가"
              물리적 배치                          권한 구조
```

|  | 중앙집중 권한 | 탈중앙 권한 |
| --- | --- | --- |
| **단일 서버** | 옛날 메인프레임 | (거의 없음) |
| **분산 서버** | **은행 시스템 · AWS** | 이더리움 · 비트코인 |

> ⚠️ **은행은 서버가 수백 대로 "분산"돼 있지만 완전한 "중앙집중"이다.** AWS도 전 세계에 분산돼 있지만 Amazon이 끄면 끝난다.
> **분산 = 성능·가용성**을 위한 것, **탈중앙 = 권력 분산**을 위한 것. 목적이 다르다.

### 선택 기준

```
중앙 DB    참가자가 한 조직. 빠르고 싸야 함          → 대부분의 업무
분산 DB    한 조직인데 규모·가용성이 필요            → 대규모 서비스
블록체인   참가자들이 서로 못 믿음. 중재자가 없어야 함  → 극소수
```

**블록체인은 성능을 버리고 "못 끄고 못 고침"을 산 것**이다. 그 교환이 가치 있는 상황에서만 쓴다.

## 4. 토론 질문

> **여러 금융기관이 데이터를 공동 검증해야 할 때 기존 DB로는 어떤 한계가 있을까?**

### 결론 먼저

**한계는 성능이 아니라 신뢰 모델이다.** 기존 분산 DB는 "참가자가 정직하다"를 **전제**하는데, 경쟁 관계인 기관들 사이에선 그 전제가 성립하지 않는다.

### ① 누구 서버에 둘 것인가 — 답이 없다

```
A은행 서버에 두면  → B, C가 "A가 몰래 고치면?" 이라고 의심
제3기관에 두면     → 그 기관을 또 믿어야 함 + 비용 + 단일 장애점
각자 따로 두면     → 데이터가 갈라짐 (현재 상황)
```

중앙 DB는 **반드시 운영 주체가 필요한데**, 경쟁사끼리는 그 주체를 정할 수 없다.

### ② 비잔틴 장애를 가정하지 않는다 ★ 핵심

| | 크래시 장애 | 비잔틴 장애 |
| --- | --- | --- |
| 증상 | 노드가 죽음. 응답 없음 | 노드가 **살아서 거짓말함** |
| 난이도 | 쉬움 (없는 셈 치면 됨) | 어려움 (누가 거짓말인지 모름) |
| 대응 | Raft, Paxos | PBFT, PoW, PoS |

**MySQL 클러스터·Raft는 크래시 장애만 가정**한다. 같은 회사 서버라 "죽을 수는 있어도 거짓말은 안 한다"가 당연한 전제다.

경쟁 기관끼리는 **이 전제가 깨진다.** A가 자기에게 유리하게 기록을 조작할 유인이 실제로 존재한다. 이 상황을 다루려면 비잔틴 장애 모델이 필요하고, 거기서 블록체인이 의미를 갖는다.

### ③ 변조를 "막는" 게 아니라 "탐지"해야 한다

중앙 DB에서 DBA가 `UPDATE` 하면 **흔적 없이 바뀐다.** 감사 로그를 둬도 그 로그 역시 같은 DBA가 지울 수 있다.

```
기존 DB   : 권한으로 막는다 → 권한 가진 사람은 통과
블록체인  : 수학으로 탐지한다 → 권한과 무관하게 걸린다
```

실습 5에서 본 그대로다. 거래 하나를 고치면 뒤 블록 전부가 어긋나 **누구나 즉시 알아챈다.**

### ④ 대사(reconciliation) 비용

현재 금융권의 실제 작업 방식이다.

```
A은행 장부 ──┐
B은행 장부 ──┼─▶ 매일 대조 → 불일치 발견 → 수작업 조사 → 정정
C은행 장부 ──┘
```

**각자 자기 장부를 들고 있어서 맞춰보는 일**이 끝없이 생긴다. 사람·시간·분쟁 비용이 실제로 크다.

공유 원장을 쓰면 **애초에 하나의 장부**라 대사할 대상이 없어진다. 이게 금융권이 블록체인에 관심을 갖는 가장 현실적인 이유다.

### ⑤ 부인 방지(non-repudiation)

```
기존 DB   : "우리 시스템 기록엔 이렇게 돼 있다"  → 상대가 부인 가능
블록체인  : 개인키 서명이 붙어 있다              → 부인 불가
```

서명은 본인만 만들 수 있으므로 "나는 그런 지시를 한 적 없다"가 통하지 않는다. 분쟁 해결 비용이 크게 줄어든다.

### 균형 잡기 — 블록체인이 만능은 아니다

토론에서 이 부분까지 말하면 좋다.

```
해결하는 것:  신뢰 문제, 대사 비용, 부인 방지, 검열 저항
해결 못 하는 것:
  · 성능 (여전히 느리다)
  · 입력 데이터의 진실성 — 쓰레기를 넣으면 '변조 불가능한 쓰레기'가 됨
  · 오프체인 세계와의 연결 (오라클 문제)
  · 개인정보 (지울 수 없으니 GDPR·개인정보보호법과 충돌)
```

> 🔴 **마지막 항목이 금융권에서 특히 중요하다.** 삭제가 불가능하다는 성질이 **개인정보 파기 의무와 정면으로 부딪힌다.** 그래서 실무에서는 개인정보를 온체인에 두지 않고, **해시값만 올리고 원본은 오프체인**에 두는 설계를 쓴다.

### 그래서 실무 답은 보통 "프라이빗 블록체인"

```
퍼블릭 (이더리움)      누구나 참여. 완전 탈중앙. 느리고 비쌈
프라이빗/컨소시엄      허가받은 기관만 참여 (Hyperledger Fabric 등)
  → 참가자를 알고 있으니 PoW 불필요 → 훨씬 빠름
  → 하지만 "서로 못 믿는다"는 전제는 유지 → BFT 합의 사용
```

금융 컨소시엄에는 **퍼블릭보다 컨소시엄 체인이 현실적**이다. 속도를 얻으면서 비잔틴 장애 대응은 유지할 수 있다.

## 5. 교재 개념 정리

### 노드 vs 피어

**같은 컴퓨터를 보는 두 관점**이다.

```
노드(Node)   네트워크에 참여한 컴퓨터 한 대   → 혼자 봤을 때
피어(Peer)   나와 직접 연결된 다른 노드       → 관계에서 봤을 때
```

P2P에 서버/클라이언트 구분이 없는 이유 — **모두가 요청도 하고 응답도 한다.**

| 노드 종류 | 보관 | 역할 |
| --- | --- | --- |
| 풀 노드 | 전체 블록 + 상태 | 모든 걸 직접 검증 |
| 라이트 노드 | 블록 헤더만 | 필요할 때 풀 노드에 질의 |
| 아카이브 노드 | 전체 + 모든 과거 상태 | 과거 시점 조회 (수 TB) |

### 브로드캐스팅 — 가십 프로토콜

전체에 한 번에 뿌리는 게 아니라 **소문 퍼지듯** 번진다.

```
1단계: 연결된 피어 8~13명에게만
2단계: 받은 피어가 또 자기 피어들에게
3단계: ... 몇 초 안에 전 세계
```

중복이 많이 생기지만 **그게 설계다** — 일부 노드가 죽거나 거짓말해도 전파가 안 끊긴다.

### 검증은 전파보다 먼저 일어난다

```
트랜잭션 수신
  ↓
① 서명이 올바른가?   ← 아니면 버림. 전파 안 함
② nonce 가 맞나?
③ 잔액이 충분한가?
④ 가스가 충분한가?
  ↓
통과한 것만 mempool 에 넣고 피어에게 전파
```

> **쓰레기는 한 홉도 못 간다.** 첫 번째 피어가 걸러낸다.

### 합의(Consensus) — 왜 필요한가

```
노드 A가 받은 순서:  tx1 → tx2
노드 B가 받은 순서:  tx2 → tx1     ← 네트워크 지연으로 흔한 일

잔액 10, tx1=송금 8, tx2=송금 5 라면
  A: tx1 먼저 → 잔액 2 → tx2 실패
  B: tx2 먼저 → 잔액 5 → tx1 실패
  → 두 노드의 DB가 영구히 갈라짐
```

**이중지불의 본질은 돈 복사가 아니라 순서 불일치**다. 해결책은 **한 번에 한 명만 순서를 정하게** 하는 것(PoW 당첨자 / PoS 제비뽑기). 나머지는 그 순서를 받아 검증만 한다.
